# Contract

The shared definitions both the app and the backend build against. Changed only by agreement, in a pull request that also updates `docs/decisions.md`. The code that implements it: `app/lib/core/article.dart`, `app/lib/core/decision_types.dart`, `app/lib/core/topics.dart`, `server/src/api/index.ts`, `server/src/translator/languages.ts` (languages), `server/src/translator/queue.ts` (the translation queue), `server/migrations/`.

## Article

What the API returns and both screens read.

```json
{
  "id": "01JA2B3C4D5E6F7G8H9J",
  "country": "PL",
  "source": { "id": "pl-mfa", "name": "Ministry of Foreign Affairs", "url": "https://www.gov.pl/web/dyplomacja" },
  "publishedAt": "2026-10-11T14:05:00Z",
  "dateOnly": false,
  "headline": "Poland condemns attack on Riyadh airport",
  "shortSummary": "Poland condemned the attack, which killed 12 people and injured more than 300.",
  "summary": "Poland's foreign ministry condemned … (news-style, 2 to 4 short paragraphs)",
  "decisionType": "decision",
  "originalTitle": "Oświadczenie MSZ ws. ataku w Rijadzie",
  "originalLanguage": "pl",
  "topics": ["foreign-affairs", "security-defence"],
  "tags": ["Saudi Arabia", "Houthis", "aviation"],
  "importance": 4,
  "imageUrl": "https://www.gov.pl/photo/… or null",
  "originalUrl": "https://www.gov.pl/web/dyplomacja/oswiadczenie-msz-ws-ataku-w-rijadzie",
  "feedSeq": 1204,
  "addedAt": "2026-10-11T15:20:00Z"
}
```

- The feed card reads `headline`, `shortSummary` and `imageUrl`; both show `decisionType` as a red label above the headline ("DECISION"); the detail screen reads `summary`. `topics` is set by the AI; the MVP app does not use it yet.
- `feedSeq` is the article's place in the feed: a number given when it is released (the AI marked it an official decision, and every enabled language has its translation: release together, below), only ever rising and never changed afterwards. `addedAt` is when that happened (column `added_at`, set with `feed_seq` and, like it, never changed by a later re-summary). The card shows `publishedAt`; the feed order follows `feedSeq`, so an article that appears late lands on top, not among the ones already read (docs/research/2026-10-15 Feed ordering for late items.md).
- Before the AI step has run, `headline`, `shortSummary`, `summary`, `decisionType` and `importance` are `null` and `topics` is `[]`; the app shows `originalTitle` instead.
- `publishedAt` is UTC. `dateOnly: true` means the source gave no time.
- Translations (#46, after the MVP): with `?lang=uk`, `ru`, `es` or `de` the API returns only articles fully translated into that language. Their `headline`, `shortSummary` and `summary` are in that language, and they have `"lang"` (`"uk"`, `"ru"`, `"es"` or `"de"`). `"feedSeq"` and `"addedAt"` are the English ones: every language has the same feed (release together). Every other field stays as it is (`originalTitle` in the original language). With `lang=en`, or without `lang`, the article is exactly as above, without `lang`.
- Release together (#46, Yurii 15 Oct): the feed is the same in every language, the same posts in the same order with the same top stories; only the language differs. A summarized decision is not shown yet: it is queued for every enabled language, and when each enabled language that is not paused has published its translation (or failed it 3 times), it is released: it gets its `feedSeq` and `addedAt` and appears in English and every language at once. English waits a few minutes too. A post that failed 3 times in a language is simply absent from that language's feed. A language whose provider is down for more than 2 hours is paused automatically, so the release stops waiting for it; it catches up when the provider is back, at the articles' own `feedSeq`, so its order still matches English. With no language enabled, an article is released at once. While the translator is not running (no run in the last 10 minutes: a new cron trigger can take about an hour to start firing, #50, or it stopped), the release waits for no translation either: the summarizer's run releases each decision at once, and every language fills in later at the English places, as after a pause.

## API

Base URL: `https://api.officialnews.workers.dev` (deployed), `http://localhost:8787` (local, `npm run dev` in `server/`).

- `GET /articles?limit=20&cursor=<c>` → `{ "items": [Article], "nextCursor": "…" | null, "top": [Article] }`: news from the last 7 days where `is_news = 1`, in the order they appeared in the feed, newest `feedSeq` first. `limit` is 1 to 50, default 20. `nextCursor` is an opaque string to send back as `cursor` for the next page, `null` on the last page. `top` is filled only on the first page (no `cursor`, no `since`): last 24 hours, highest importance, at most 2 per country, up to 5, listed newest `feedSeq` first; otherwise `[]`. It may be empty, so the app must not depend on it. Top articles also appear in `items`.
- `GET /articles?after=<feedSeq>` → only articles that appeared after that `feedSeq`, late ones included: the "N new" check. The app sends the highest `feedSeq` it holds.
- `GET /articles?since=<ISO time>` → kept for app builds before `after`, which send the publication time of the first article they show: returns articles with a higher `feedSeq` than the newest article published at or before that time (the one those builds show first), so late articles count once and only when they are new.
- `GET /articles/:id` → `Article` shown in the feed, or 404 (hidden articles, and articles not released yet, too).
- `lang` (#46) on both: `en`, `uk`, `ru`, `es` or `de` (the list is `LANGS` in `server/src/translator/languages.ts`, plus `en`). `en`, or no `lang`, is the English feed above, unchanged. With any other, consistency comes first: an article shows in that language only when its translation is finished, never as English mixed in.
  - `GET /articles?lang=uk&limit=20&cursor=<c>` → `{ "items": [Article], "nextCursor": "…" | null, "top": [Article], "translationsDelayed": false }`: the English feed above, the same articles in the same order (`feedSeq`), keeping those with a shown translation into that language. `cursor`, `nextCursor`, `after=<feedSeq>` and `since` work exactly as in English, and a cursor is valid in every language (the same positions). `top` (first page only) is the English top stories that are translated into that language, in the same order, so it may have fewer. `translationsDelayed` is `true` while the language is paused (automatically, its provider down for more than 2 hours, or by hand) or turned off: its newest articles may be missing for a while, and the app can say so. It is only in language feeds.
  - `GET /articles/:id?lang=uk` → the translated `Article`, or 404 when the article is not released or not translated into that language: not yet, never (after 3 unusable answers), or no longer (its English was summarized again and the new English got 3 unusable answers, so the old translation no longer matches it).
- `GET /health` → `{ "sources": { "<status>": <count> }, "lastFetcherRun": "<ISO time>" | null }`.
- `GET /queue` (#46) → the translation queue per language, read-only, no secrets, `cache-control: no-store`:
  ```json
  { "languages": { "uk": { "enabled": true, "paused": false, "pausedReason": null, "downSince": null,
                           "queued": 0, "updating": 0, "translating": 0, "retrying": 0,
                           "published": 120, "failed": 1, "skipped": 0, "publishedLast24h": 40,
                           "oldestWaitingAgeMinutes": null, "lastPublishedAt": "2026-10-15T14:02:11Z" }, "ru": { … }, "es": { … }, "de": { … } },
    "release": { "waiting": 2, "oldestWaitingAgeMinutes": 3, "translatorRanAt": "2026-10-16T08:14:00Z" } }
  ```
  One entry per language of `LANGS`, with its switch (`pausedReason`: `"manual"`, or `"auto: provider down since <time>"` for an automatic pause; `downSince`: since when its providers have not answered, or `null`), the count of translations in each state (below), how many were published in the last 24 hours, the minutes since the oldest one still waiting (`queued`, `updating`, `translating` or `retrying`) was queued (`null` when none waits), and when the last one was published. `release`: how many summarized decisions wait for their release (their translations), and the minutes since the oldest of them was summarized. It reads about 20 D1 rows, however many translations exist: the counts come from `translation_counts`, the rest through partial indexes. Managing the queue is `server/scripts/queue.mjs` (`docs/queue.md`).
- Errors are JSON `{ "error": "<message>" }`: 400 for a bad `limit`, `cursor`, `after`, `since` or `lang`, 404, 405 for any method other than GET, 500.
- `GET /articles/:id` → `Article` shown in the feed, or 404 (hidden articles too).
- `GET /health` → `{ "sources": { "<status>": <count> }, "lastFetcherRun": "<ISO time>" | null, "articles": { "fetchedLast24h": <n>, "waitingForSummary": <n>, "inFeed": <n> } }`: real sources only (seed rows skipped); `lastFetcherRun` is the latest `last_checked_at`; `inFeed` counts official decisions of the last 7 days. Open in a browser to see whether the fetcher and the AI step are running.
- Errors are JSON `{ "error": "<message>" }`: 400 for a bad `limit`, `cursor`, `after` or `since`, 404, 405 for any method other than GET, 500.

## Database (D1)

Defined in `server/migrations/0001_init.sql`.

- `sources`: id, country, name, kind (`rss` | `page` | `api`), url, config (JSON: selectors for pages), language, verified_by (`domain` | `portal` | `wikidata`), verified_at, licence, status (`active` | `stale` | `moved` | `broken` | `blocked`), last_checked_at, last_item_at, list_etag, list_last_modified (the list's validators, kept by the fetcher for sources with `conditionalGet`; migration `0003`), failed_checks, last_ok_at, last_error (source health, migration `0007`)
  - The source list lives in `docs/sources.csv` (one row per source, with how it was verified as official). The deploy loads it into the live database on every change (`npm run sources:local` for a laptop). Loading adds or updates rows and never changes `status` or the check times, which the fetcher and health checks own.
  - Rows with `config` `{"seed": true}` come from the Kickoff seed so the app has data; the fetcher and the health checks skip them.
- `articles`: id, source_id, url (unique), original_title, published_at, date_only, fetched_at, text, text_expires_at, headline, short_summary, summary, image_url, original_language, topics (JSON), tags (JSON), importance, decision_type, is_news (NULL until the AI decides, 1 = official decision shown in the feed, 0 = hidden), summarized_at, model, summary_attempts (migration `0004`), summary_claimed_at (migration `0005`), feed_seq (unique; migration `0006`; given by the release step, `server/src/translator/release.ts`, at the end of each translator and summarizer run, MAX + 1 in one statement per article, oldest summarized first; migration `0010` moved it there from the summarizer), added_at (when feed_seq was given). `is_news = 1` with no `feed_seq` is a decision waiting for its release (index `articles_unreleased`).
- `article_translations` (migration `0008`, #46; it was `0007` until #55 took that number): article_id, lang, headline, short_summary, summary, model (`groq:<model>` that wrote it), source_summarized_at (the article's `summarized_at` when the English was translated), lang_seq, translated_at, claimed_at, attempts, attempts_source (the `summarized_at` of the English the queue holds for it, which the attempts count for), queued_at (when that English was queued; NULL when nothing waits). One row per article and language (primary key `article_id, lang`), which is also its place in the translation queue. A row exists from the moment the translator queues the article for that language, and is finished once its texts (and `lang_seq`) are set.
  - `lang_seq`: the order in which that language's first translations were stored (the language's highest plus 1, set with `translated_at`; neither ever changes; a unique index on (`lang`, `lang_seq`) refuses a number given twice). Since migration `0010` it orders nothing: every language feed follows `articles.feed_seq`. The column stays because the all-or-nothing CHECK reads it.
  - All or nothing: a CHECK constraint lets a row have either none of headline, short_summary, summary, model, source_summarized_at, lang_seq and translated_at, or all of them (the three texts not empty).
  - The queue (migration `0009`, was `0008`): state (below), state_at (when it entered that state), next_attempt_at (`retrying`: not claimed before), last_error (why it is `retrying`, `failed` or `skipped`), published_at (when the text shown was published; `translated_at` is the first time), outage_retries (tries no provider answered, for the backoff; never an attempt). `queued_at` is set while it waits (`queued`, `updating`, `translating`, `retrying`) and NULL otherwise.
  - States: `queued` (waiting for its first translation) → `translating` (claimed by a run, `claimed_at`) → `published` (the translation of the current English is shown). `retrying` (an unusable answer, `attempts` + 1, waits 10 then 20 minutes; or no provider answered, no attempt, waits 2, 4, 8 … up to 60 minutes) until `next_attempt_at`. `failed` after 3 unusable answers for one English, with the reason; not shown until the English changes, except a text of that same English (requeued by hand, its redo failed), which still matches it and stays shown. `updating`: the English was summarized again; the old translation is shown until the new one is published. A claim older than 10 minutes goes back to `queued` (or `updating`). `skipped`: the article left the feed (hidden, older than 7 days) or its English is being redone, with why; a new English queues it again.
- `translation_langs` (migration `0009`): lang (primary key), enabled, paused, updated_at; paused_reason and down_since (migration `0010`). The switch per language: only an enabled language is queued and waited for by the release. A paused one is queued, but the release no longer waits for it. Paused by hand (`queue.mjs pause`, paused_reason `manual`), nothing of it is claimed until `resume`. Paused automatically (paused_reason `auto: provider down since <time>`, when down_since is more than 2 hours old), it is still probed with one claim a run, and its first answer unpauses it. down_since: the first try of the current outage that no provider answered (or the first run without its provider key); cleared by any answer. Migration `0009` enabled `uk`, `ru`, `es` and `de`; `0010` turns `de` off (Z.ai blocks Cloudflare Workers).
- `step_runs` (migration `0011`): step (primary key), at. When a scheduled step last ran: the translator writes `translator` at the start of every run, and the release waits for translations only while that is less than 10 minutes old (`TRANSLATOR_ALIVE_MINUTES`).
- `translation_events` (migration `0009`): article_id, lang, state, at, attempts, detail (the model for `published`, the reason for `retrying`, `failed`, `skipped` and a claim that ran out). Every change of state of `article_translations`, written by a trigger, whoever makes it (the translator or `queue.mjs`); kept 30 days.
- `translation_counts` (migration `0009`): lang, state, n. How many translations each language has in each state, kept by triggers on `article_translations`, for `GET /queue`.

Times (`published_at`, `fetched_at`, `summarized_at`, `text_expires_at`, `translated_at`, `claimed_at`, `source_summarized_at`, `attempts_source`, `queued_at`, `state_at`, `next_attempt_at`, the translation's `published_at`, `translation_events.at`, `translation_langs.updated_at`, `translation_langs.down_since`, `added_at`, `step_runs.at`) are stored in UTC as `YYYY-MM-DDTHH:MM:SSZ`, without milliseconds, so they sort and compare as text.

## Scheduled job

Three cron triggers (`server/wrangler.jsonc`), each its own run with its own free-plan budget of at most 50 outside requests and 10 ms of CPU. Every minute (`* * * * *`), `runFetcher(env)` (item 6) takes the source with the oldest `last_checked_at`. Every odd minute (`1-59/2 * * * *`), `runSummarizer(env, { maxArticles: 5 })` (item 7) makes one AI call per article. Every even minute (`0-58/2 * * * *`), `runTranslator(env, { maxTranslations: TRANSLATIONS_PER_RUN })` (#46) makes up to 4 translations: one article in each language, also when the other languages have nothing to do or are paused; then it releases the articles that are ready into the feed. `server/src/index.ts` picks the step by `controller.cron` (`CRONS`; a test checks it knows every trigger in `wrangler.jsonc`). A newly added Cloudflare schedule can take about an hour to start firing (#50: the summarizer's started about 55 minutes after the deploy), so check `wrangler tail` an hour after the deploy before calling it broken. Locally: `npx wrangler dev --test-scheduled`, then open `/__scheduled?cron=1-59/2+*+*+*+*` for the summarizer or `/__scheduled?cron=0-58/2+*+*+*+*` for the translator (any other `cron` runs the fetcher).
Two cron triggers (`server/wrangler.jsonc`), each its own run with its own free-plan budget of at most 50 outside requests and 10 ms of CPU. Every minute (`* * * * *`), `runFetcher(env)` (item 6) takes the source with the oldest `last_checked_at`. Every odd minute (`1-59/2 * * * *`), `runSummarizer(env, { maxArticles: 5 })` (item 7) makes one AI call per article. Once a day at 03:17 UTC (`17 3 * * *`), `runCleanup(env)` (item 8) clears old texts. Right after each fetcher run, `recordChecks(env, checks)` (item 8) gives the checked sources their status. `server/src/index.ts` picks the step by `controller.cron` (`CRONS`). Locally: `npx wrangler dev --test-scheduled`, then open `/__scheduled?cron=1-59/2+*+*+*+*` for the summarizer (any other `cron` runs the fetcher).

What the fetcher writes (`server/src/fetcher/`):
- Only items published in the last 7 days; an item already stored (same `url`) is never saved again. Items without a date are skipped, and a time later than the fetch is stored as the fetch time.
- Only links on the source's own site (its host or a subdomain, or a host in `config.allowedHosts`), always as `https`.
- A run claims its sources first (sets `last_checked_at` in the same statement that picks them), so a run cut off by a limit never blocks the others.
- New articles: `is_news` `NULL` (the AI decides), `original_language` from the source, `text` up to 20,000 characters with `text_expires_at` 30 days after `fetched_at`, `image_url` from the list or the item page's preview image.
- A date without a time is stored at 12:00 UTC (or the fetch time if that is earlier) with `date_only = 1`.
- `url` may end in `#…` when one link holds several items (bill stages); the part before `#` is the page.
- Every check sets `last_checked_at`; `last_item_at` is the newest item seen. `runFetcher` returns one `SourceCheck` per source (`ok`, `httpStatus`, `found`, `saved`, `waiting`, `undated`, `offSite`, `error`), which source health (item 8) can use, and logs it as JSON.

What source health writes (`server/src/health/`, item 8):
- After every check, the source's `status`: `active` when the check worked and the source listed an item from the last 14 days; `stale` when it worked but nothing listed is newer; `broken` after 3 failed checks in a row (no answer, robots.txt, an HTTP error); `moved` the same, when the list page answers 404 or 410. One failed check keeps the status. `failed_checks` counts the failures in a row, `last_ok_at` is the last check that worked, `last_error` why the last one failed.
- `blocked` is set by people (`docs/sources.csv`) and never changed by health. The fetcher keeps checking `broken`, `moved` and `stale` sources, so a source that recovers turns `active` on its next good check.
- Once a day: `text` is cleared where `text_expires_at` has passed (30 days after fetching). Title, summary and link stay; a later re-summary of such an article works from its title.

What the summarizer writes (`server/src/summarizer/`, rules in `docs/style-guide.md`):
- It takes articles with no `summarized_at`, newest `fetched_at` first, also those with only a title.
- One call to Workers AI (`@cf/zai-org/glm-4.7-flash`) fills `headline`, `short_summary`, `summary`, `decision_type`, `topics`, `tags`, `importance`, `is_news`, `summarized_at` and `model`. `is_news` 1 makes it a decision waiting for its release, which gives it its `feed_seq`, in every language at once. The summarizer gives no `feed_seq`; its scheduled run ends with the release (logged as `summarizer release`), so decisions reach the feed also while the translator is not running.
- An unusable answer adds 1 to `summary_attempts`; after 3 the article stays hidden. An error from Workers AI itself (an outage, or the day's free allocation used up) costs no attempt and ends the run.
- A run claims its articles first (sets `summary_claimed_at` in the same statement that picks them), so an overlapping run takes other ones. A claim older than 10 minutes is from a run that was cut off and no longer counts; an error from Workers AI frees the claims at once.

What the translator writes (`server/src/translator/`). Consistency first, speed second: an article shows in a language only once its translation is complete and checked, and the feed is the same in every language (release together).
- The queue (`queue.ts`, states above): every news article in the feed (`is_news = 1`, summary fields and `summarized_at` filled, last 7 days) enters it once per enabled language and English version, also for a paused language or one without its provider key, so nothing is lost. Each run, in one batch before any AI call: drops the state log older than 30 days, sends claims older than 10 minutes back to `queued`, queues the news whose `summarized_at` is newer than the newest it has queued for that language (less 10 minutes, for a summary written a moment after its time) through an index, marks a language without its provider key as down, and claims, in one statement, one translation per language (`CLAIMS_PER_LANGUAGE`) in each language that is enabled, not paused by hand and has a provider: of what waits (`queued`, `updating`, or `retrying` that is due), an article not released yet first (the whole feed waits for it), then the oldest English, so a language catching up after a pause holds back no new article, and one language's backlog or outage never holds back another. Of the first 4 waiting rows it reads per language (`CLAIM_WINDOW`, plus 4 of articles not released yet), those whose article left the feed become `skipped` and take no place in the run. A language with nothing queued yet (a new one) queues the feed's 7 days. Each language's waiting rows are read through their own partial index, so a run reads about what it takes, also when a paused language has a backlog: a run with nothing to do reads about 80 D1 rows (the switches and the release included), however many articles the feed holds, and one article in four languages writes about 130 (the state log and the counts included).
- One AI call per article and language: headline, short summary and summary from English into the language, nothing else. The other fields are never translated.
- Providers per language, in order, from one constant (`TRANSLATORS` in `index.ts`): Ukrainian `groq:qwen/qwen3.8-27b`, then `groq:openai/gpt-oss-120b`; Russian `groq:openai/gpt-oss-120b`, then `groq:qwen/qwen3.8-27b`; Spanish `groq:openai/gpt-oss-20b`, then `groq:openai/gpt-oss-120b`; German `zai:glm-4.5-flash`, then `zai:glm-4.7-flash` (German is off by default: Z.ai answers requests from Cloudflare Workers with an HTTP 405 block page). `max_tokens` 700, temperature 0.2, JSON mode. Groq needs the Worker secret `GROQ_API_KEY`, Z.ai `ZAI_API_KEY`; without its key a language waits in the queue and the run logs it under `waiting`. Z.ai (`POST https://api.z.ai/api/paas/v4/chat/completions`, `thinking: {"type": "disabled"}`) gets one request at a time: a run makes its requests one after another. No Workers AI for translations for now (`workers-ai:<model>` works in the same constant if that changes).
- The answer is checked as a whole: valid JSON with all three fields, not cut off, each at most twice the English length (plus 20 characters), the summary with the English's number of paragraphs, and every field in the language (`server/src/translator/prompt.ts`):
  - Ukrainian and Russian, field by field: for Ukrainian none of ы, э, ъ, ё and none of a short list of Russian-only words (и, что, его, как, также, …), and at least one of і, ї, є, ґ in the answer and in every field of 100 letters or more; for Russian none of і, ї, є, ґ and none of a short list of Ukrainian-only words (що, це, його, також, …). Paragraph by paragraph and sentence by sentence: Cyrillic letters in every paragraph, and in every sentence more of them than letters of Latin words in lower case (untranslated English).
  - Spanish and German use the English letters, so the check counts short function words instead (`server/src/translator/words.ts`; no word is on two lists): in no sentence may English or the other of the two have more of them than the language's own; a field of 8 words or more needs at least one of its own; and a field may not be the English unchanged. A function word inside a name does not count: in lower case between capitalised words (`Bank of England`, `Ministerio de Sanidad`, also past a second name particle: `Ursula von der Leyen`, `Sindicatura General de la Nación`), capitalised after the start of a sentence (a name or a German noun: `in Not`), and one of the other language capitalised at the start before a capitalised word (`Los Angeles`, `El Salvador`, `Von der Leyen`, `Die Linke`); an English one at the start counts. Acronyms (`IT`, `WHO`, `UN`) are no function words, and a word the language itself uses is not foreign to it (German `los` and `her`, Spanish `bis`).
  - Names, acronyms and brands, quoted titles, parentheses and links may stay in their own language.
- No missing information (`server/src/translator/numbers.ts`): every number of each English field must be in the same translated field, each by a number of its own ("5 ministers in 5 regions" needs two fives, and the 5 of "3,5" is not a dropped "5"), compared by value, so the language's own format passes: 1,250,000 = 1 250 000, 3.5% = 3,5 %, 11:59pm = 23:59 or 23.59, 5pm = 17:00 or 17, 16.30 hours = 16:30. A word for millions or more after a number is read with it, on both sides, so €2.86 billion = 2.860 millones = 2 860 млн = 2,86 Milliarden (thousands in words are not: 500 тисяч for 500,000 is missing). In all four languages a comma is the decimal mark, so English thousands copied unchanged ("1,500") are missing, except in an identifier after №, Nr., n.º, núm. or No. (Law No. 9,394). In Spanish and German a full stop only groups thousands (1.250.000), so "3.5" copied from the English is missing too, and 17.00 is a time (17.00 Uhr). A date in numbers (15.10.2026, 14/10/2026, 2026-10-14) needs its day, its month (in numbers or by name: 15 жовтня, 15 de octubre, 15. Oktober) and its year; 5575/2026 is two numbers. The prompt asks for the language's number format (`1 250 000; 3,5 %` in Ukrainian and Russian, `1.250.000; 3,5 %` in Spanish and German).
- All or nothing: the three fields, the model and `source_summarized_at` are stored in one statement, which also makes it `published` and gives a first translation its `lang_seq` and `translated_at` (bookkeeping: the feed's order is the article's `feed_seq`). A partial or unusable answer stores nothing.
- English changes: when the article is summarized again, its new `summarized_at` puts it back in the queue with fresh tries, as `updating`. The old translation is served until the new one is published in its place (the article keeps its `feed_seq`), or until the new English has had 3 unusable answers (`failed`): then the article no longer shows in that language, since the old text no longer matches the English, until a later English is translated. A translation is stored only for the English the queue holds, never over a translation of a newer English, and only while the run's claim holds: a requeue made meanwhile (`queue.mjs requeue`) is not undone, and a claim that ran out is not stored twice.
- A provider that fails for a reason that is not the article's (HTTP 429, 5xx, network, quota; for Z.ai also error codes 1302, 1305 and 1234) is skipped for the rest of the run and the next one is tried; when none answers, the translation is `retrying` with a growing wait (2, 4, 8 … up to 60 minutes) and no attempt is counted. Only the run holding a claim changes its state or stores its text.
- An unusable answer (including Z.ai's content filter, error 1301 or `finish_reason` `sensitive`) adds 1 to `attempts`: `retrying` 10, then 20 minutes later; after 3 that English is `failed` with the reason: a new article does not show in that language, and a re-summarized one no longer shows its old translation, until the English changes again (the attempts count per English version, `attempts_source`).
- Release (`release.ts`), at the end of every run, also one with nothing to translate, and of every summarizer run: each article with `is_news = 1` and no `feed_seq` whose translations are ready gets `feed_seq` (MAX + 1, one statement per article, oldest `summarized_at` first, so the English order is kept) and `added_at` = now. Ready: for each language of `LANGS` that is enabled and not paused, its row for the article's current English is `published` or `failed`. Also released at once: every article while the translator has not run for 10 minutes (it records each run in `step_runs`), an article published before the feed's 7 days (shown nowhere) and one without an English summary. A visible row without a number from an older Worker is released this way too, not lost.
- Automatic pause: a language whose providers did not answer (every one down, rate limited or out of quota; or no provider key) is down from that try (`down_since`); any answer, usable or not, clears it. After 2 hours down (`AUTO_PAUSE_HOURS`), the run pauses it (`paused_reason` `auto: provider down since <time>`), and the release stops waiting for it; it is still claimed from, one translation a run, and the first answer unpauses it. Its missing translations then fill in at the articles' `feed_seq`. A pause by hand is never undone by the translator.
- Logs one `translator start` line (what it claimed, how many translations it queued, claims that ran out, any it skipped, languages waiting for a key) before any AI call and one `translator run` line with the result per article and language and the provider used, plus the articles `released`, languages `autoPaused` and `resumed`; a run that only queued, released or skipped something logs one `translator queue` line, and one with no provider key at all `translator skipped`.
