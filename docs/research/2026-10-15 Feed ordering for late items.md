# Sort by arrival, keep the official date

Sort the feed by the moment each article becomes visible, not by its official publication time. Build that order as a number the server hands out and that only ever goes up: option A, built on option C's sequence. In practice, each article gets a `feed_seq` in the same database write that marks it as news (`is_news = 1`). The feed lists articles by that number, newest first, and every card still shows the official publication date. A new number can never be smaller than one the phone already holds, so a late article can only land above everything the reader has seen. That removes the overnight problem (12 of 25 items landing mid-list) by design, not by tuning. The same number also drives infinite scroll and an exact "N new" count, so the three can never disagree. FreshRSS, Inoreader, Feedly, Hacker News, X and Mastodon all order their feeds this way. Bluesky sorts by the author's own timestamp, as the app does today, and it documents the same blind spot the app now has. Option B only fixes the "new" indicator, leaves late items mid-list in the main feed, and still needs the sequence to find them. Full option C (an offline copy on the phone, kept current with deltas, deletion records and a reset path) works, but it is more machinery than a ~500-item window needs, and adding the sequence column now keeps that option open. The price of A is cosmetic: a decision published at 09:00 can sit above one published at 11:00 because its AI step finished later, and every product that sorts by arrival accepts that. A "For you" tab can come later as a re-ranking of the same window on the phone, with the chronological list kept as the default or one tap away.

## Mature feeds sort by arrival, and the one exception documents this exact bug

The large RSS readers decided this long ago, and they wrote down why. **FreshRSS sorts by received date by default.** Publication-date sorting arrived only as an option, in a 2025 pull request whose author argued that received order is the right default because "new entries always have a higher received date" ([FreshRSS PR #7149](https://github.com/FreshRSS/FreshRSS/pull/7149)). The same PR lists what breaks under any other sort. Publication dates are not unique and not monotonic. They can sit far in the future, or show up later dated far in the past. With a non-received sort, the actions that mark items older than a day or a week as read are disabled, the Today/Yesterday headers disappear, and API sync loses its guarantees ([FreshRSS PR #7149](https://github.com/FreshRSS/FreshRSS/pull/7149)). Inoreader's API tells developers the publisher's `published` field is for display only and to use its own receive timestamp instead ([Inoreader API](https://www.inoreader.com/developers/stream-contents)). Feedly's help pages say the date it shows is when Feedly added the article to its system, and that this can differ from publication by minutes or hours ([Feedly help](https://docs.feedly.com/article/323-my-article-is-showing-the-wrong-date)). Hacker News "newest" runs strictly in item-ID order, and its "More" link is a cursor on that ID ([HN newest](https://news.ycombinator.com/newest); [HN API](https://github.com/HackerNews/API)).

Social timelines reached the same answer. **X sorts and pages by IDs the server creates when a post is created**: 64-bit Snowflake values that run in roughly time order and are read with `since_id` and `until_id` ([X Docs: X IDs](https://docs.x.com/resources/fundamentals/x-ids); [X timelines guide](https://docs.x.com/x-api/posts/timelines/integrate)). Mastodon is the closest analogue to this app, because its posts, like government decisions, arrive from elsewhere already carrying their own timestamp. **In 2018 Mastodon changed live-delivered posts to take IDs based on when its server processed them**, because backdated IDs broke a promise every paging client relied on: a new item always has a larger ID than the last one seen ([Mastodon PR #7336](https://github.com/mastodon/mastodon/pull/7336)). That rule is still in Mastodon's main branch, and each user's home feed is a sorted set scored by exactly that ID ([snowflake.rb](https://github.com/mastodon/mastodon/blob/main/lib/mastodon/snowflake.rb); [feed_manager.rb](https://github.com/mastodon/mastodon/blob/main/app/lib/feed_manager.rb)).

Bluesky is the exception, and it shows what the app has today. Its server sorts every chronological feed by **the earlier of the author's `createdAt` and the time the server first saw the post** ([Bluesky docs: Timestamps](https://github.com/bluesky-social/bsky-docs/blob/main/docs/advanced-guides/timestamps.md); [atproto schema](https://github.com/bluesky-social/atproto/blob/main/packages/bsky/src/data-plane/server/db/migrations/20230309T045948368Z-init.ts)). That rule stops future-dated spam from pinning itself to the top. For any post indexed late, though, it falls back to the author's time and slots the post behind items the reader may already have passed. When Bluesky added a "newer than" bound to its timeline API in September 2026, the same pull request acknowledged that items landing later below the bound are invisible to such reads, and told clients to do an occasional full refresh ([atproto PR #5493](https://github.com/bluesky-social/atproto/pull/5493)). Its app's "new posts" check fetches only the single newest item, so a late post never lights the indicator ([post-feed.ts](https://github.com/bluesky-social/social-app/blob/main/src/state/queries/post-feed.ts); [following.ts](https://github.com/bluesky-social/social-app/blob/main/src/lib/api/feed/following.ts)). The app's current contract follows the same pattern: the feed is sorted by `published_at`, and the "new updates" check `since=<ISO time>` also filters on `published_at` (`docs/contract.md`, `server/src/api/index.ts`). In this app every item is late, because the fetcher and the AI step always add delay, so every item behaves like Bluesky's worst case. The overnight 12-of-25 result is what that design predicts, not bad luck.

Arrival-ordered feeds still need two guards against odd dates, and the app already has both. Future dates are clamped by NewsBlur ([NewsBlur forum](https://forum.newsblur.com/t/override-or-delay-future-dating-of-publisher-content-channeled-through-newsblur/6605)) and Mastodon ([snowflake.rb](https://github.com/mastodon/mastodon/blob/main/lib/mastodon/snowflake.rb)); the app's fetcher already never stores a time later than the fetch (`docs/decisions.md`, 2026-10-14). For stale backfills, **Mastodon puts posts that were not delivered live into home feeds only if they are under 6 hours old** ([status.rb](https://github.com/mastodon/mastodon/blob/main/app/models/status.rb)). Apple News added a `datePublished` field in 2016 so back-catalogue stories would not appear as new, according to press coverage at the time ([AppleInsider](https://forums.appleinsider.com/discussion/193118)). The app's 7-day window on publication date does this job. Under A, the worst case is a source that comes back after an outage and puts a few articles dated several days ago at the top, each showing its true date. No product surveyed publishes a numeric rule for this. Google's nearest equivalent is limiting news sitemaps to articles from the last two days ([Google: News sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/news-sitemap)). Measure the actual delay between publication and visibility before adding any threshold.

## One number that only rises keeps order, scrolling and the pill in step

Paging alone does not cause the mid-list problem; the sort key does. Offset paging is the known-broken option. Slack's engineering team describes page two repeating page one after ten new messages arrive ([Slack Engineering](https://slack.engineering/evolving-api-pagination-at-slack/)), and Markus Winand shows that counting skipped rows produces duplicates whenever rows are inserted ([Use The Index, Luke](https://use-the-index-luke.com/no-offset)). The app already uses the fix, a keyset cursor, which never repeats or skips rows that already exist. But a keyset cursor walks in one direction only, so **a row whose key falls into the region already read is never returned in that pass**. With `published_at` as the key, every late article does exactly that. With a key handed out at visibility, no article can land behind the cursor, and the same cursor becomes correct by design.

A timestamp is not enough as that key. Google's Calendar API calls its old timestamp-based "modified since" sync no longer recommended because it misses updates more easily ([Google Calendar sync guide](https://developers.google.com/workspace/calendar/api/guides/sync)). Replicache, a sync library, explains why: a write that started earlier can commit after a reader has already moved past its timestamp, and that change is then never sent ([Replicache: Global Version](https://doc.replicache.dev/strategies/global-version)). Even integer sequences can commit out of order in a database with many concurrent writers, such as Postgres ([cloudscale](https://www.cloudscale.ch/en/engineering-blog/2025/10/09/generating-truly-sequential-ids-in-postgresql)). This applies here directly. The app's `summarized_at` is set from the Worker's clock before the UPDATE runs, at one-second precision (`server/src/summarizer/index.ts`). Two summarizer runs can therefore tie, or commit their timestamps out of order. It works as a displayed "added at" time, but not as the sort key or the cursor. D1 avoids the commit-order problem if the number is calculated inside the SQL statement itself. **Each D1 database is single-threaded and processes queries one at a time** ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)), and batched statements run one after another as a single transaction ([D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)). That commit order matches execution order is an inference from those statements, not something Cloudflare states, so it needs one test (see the last section). The plain row ID will not do. It is assigned at insert, which is fetch time, not visibility, and without AUTOINCREMENT SQLite can reuse it ([SQLite AUTOINCREMENT](https://www.sqlite.org/autoinc.html)). Gaps in the sequence are harmless; Gmail's history IDs have them by design ([Gmail history.list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list)).

The "N new" pill is a settled pattern. In 2018 Instagram replaced its auto-jump to the top with a New Posts button: tap to go to the new posts, or stay where you are ([Instagram](https://about.instagram.com/blog/announcements/new-posts-button-to-improve-instagram-feed)). WCAG 2.2 criterion 2.2.2 requires a way to pause, stop or hide auto-updating content shown alongside other content, and names news as an example ([W3C: Understanding SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)). Bluesky polls every 60 seconds, shows a "load latest" button when the user is scrolled down, and scrolls to the top on tap ([FeedPage.tsx](https://github.com/bluesky-social/social-app/blob/main/src/view/com/feeds/FeedPage.tsx)). With a sequence, the phone keeps the highest number it holds and asks the server how many items are above it. **The count is exact and includes late items.** That is something neither Bluesky's one-item check nor the app's current `since=<published time>` can promise. If the reader is already at the top, new items can simply appear. If there are more new items than one page holds, the app reloads from the top instead of fetching only the newest page and leaving a hole. That hole is the reason Mastodon has a separate gap-free `min_id` parameter ([Mastodon API guidelines](https://docs.joinmastodon.org/api/guidelines/)).

The same rule covers "new since last visit" and any future "mark all read": store the highest sequence number the reader saw, never a date. NewsBlur kept a "last read date" taken from story dates. One future-dated story pushed that mark forward and hid genuinely new stories until real time caught up ([NewsBlur forum, 2012](https://forum.newsblur.com/t/posts-from-the-future/600)). FreshRSS caps mark-all-read at the highest received ID displayed for exactly that reason ([FreshRSS PR #7149](https://github.com/FreshRSS/FreshRSS/pull/7149)). Caching follows from this design. If feed pages are ever cached at the edge, the "anything new?" check must bypass the shared cache, which is MDN's guidance for frequently updated content ([MDN: Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)). Using the current top sequence number as the ETag would make an unchanged answer a cheap 304. That is a design inference, consistent with GitHub's advice that stable conditional requests save quota ([GitHub REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)).

## Options B and C each fix the wrong half of the problem

Two questions are easy to blur: *who* sorts (the server or the phone), and *by what key*. Only the key decides whether late items land mid-list. Option C changes who sorts, and option B adds a second list, but neither changes the key of the main feed.

| | A: server sorts by visibility sequence | B: publication order + "new since last visit" block | C: sequence sync, phone stores and sorts locally |
|---|---|---|---|
| Late item lands mid-list in the main feed? | Never, by construction | Yes, unchanged from today | Yes if the phone sorts by publication date; no if it sorts by sequence, which is A |
| "N new" count exact? | Yes | Only if the block uses a sequence; `since=<publication time>` misses late items | Yes |
| Infinite scroll stable? | Yes, keyset on one unique integer | Existing rows yes; late rows behind the cursor are never returned in that pass | Not applicable: the whole window is local |
| Card dates in strict order? | Mostly; a late item can show an earlier date above a later one | Yes | Depends on the local sort |
| New moving parts | One column, one index, one parameter, the pill | The sequence plus a second list and duplicate handling | Local database, deletion records, reset path, saved cursor |
| Precedent | FreshRSS, Inoreader, Feedly, HN, X, Mastodon | Bluesky, which documents the blind spot | Gmail, Google Calendar, CloudKit, CouchDB |

B deserves a fair hearing, because an official record has a natural order: the order in which governments published. Gazettes and registers read that way, and matching the order to the dates on the cards looks tidy. But B leaves the main list exactly as broken as today. A reader who scrolls the feed instead of tapping the block still meets late items buried below ones they have read. And the block itself needs a reliable "what became visible since my last visit" signal, which publication time cannot provide, so B must build A's sequence anyway. It also shows each late item twice, once in the block and once in the list, so it needs duplicate-handling rules. If ordering by official date matters to some readers, it fits better as a secondary sort option later, the way FreshRSS offers it with its trade-offs documented ([FreshRSS PR #7149](https://github.com/FreshRSS/FreshRSS/pull/7149)).

Full C is the industry pattern for keeping a copy in sync, and its parts are well documented. The phone stores one opaque position and asks for changes since it, deletions arrive as records, and an explicit "too old, start over" error forces a full resync: Gmail returns 404, Calendar 410, Dropbox a 409 reset ([Gmail sync guide](https://developers.google.com/workspace/gmail/api/guides/sync); [Calendar sync guide](https://developers.google.com/workspace/calendar/api/guides/sync); [Dropbox: detecting changes](https://docs.dropboxapi.com/dropbox-api/docs/detecting-changes)). Each of those parts is a place for bugs. Replicache warns that a phone which saves its cursor ahead of its data will never receive the missing rows ([Replicache: Global Version](https://doc.replicache.dev/strategies/global-version)). It also says plainly that resending everything works when data is very small or changes rarely ([Replicache: Reset](https://doc.replicache.dev/strategies/reset)). The whole 7-day window is roughly 0.5–1 MB without full text (an estimate, not measured), so it qualifies. C earns its keep once the app wants offline reading or "updated" badges. When it does, it needs a *second* change counter that moves on edits and hides, because the order key must never move once assigned. Mastodon re-surfaces a post by creating a new item with a new ID (a boost), never by renumbering the original ([feed_manager.rb](https://github.com/mastodon/mastodon/blob/main/app/lib/feed_manager.rb)).

The honest cost of A is the occasional date that looks out of order. Mastodon accepts that a post's displayed time and its feed position can differ ([Mastodon PR #7336](https://github.com/mastodon/mastodon/pull/7336)). Feedly sidesteps it by showing the time it added the article instead of the publication date ([Feedly help](https://docs.feedly.com/article/323-my-article-is-showing-the-wrong-date)). For an official-news product the official date is part of the credibility, so keep showing it. Most delays are minutes to hours, so the disorder stays within a day. If it bothers testers, a small "added 11:40" note on items that became visible long after publication explains the order without changing it.

## "For you" re-ranks the same window on the phone, and "Latest" stays one tap away

The big platforms all run personalization as a separate pipeline over the same pool of items. **Twitter's open-sourced Home Mixer builds "Following" and "For You" on the same framework.** Following returns reverse-chronological posts with no scoring stage, while For You adds candidate sourcing, about 6,000 features, machine-learning scoring and diversity rules ([Home Mixer README](https://github.com/twitter/the-algorithm/blob/main/home-mixer/README.md)). Facebook narrows more than a thousand candidates per user per day to about 500 in a cheap first pass before its main scoring ([Engineering at Meta](https://engineering.fb.com/2021/01/26/core-infra/news-feed-ranking/)). The app's entire window is about that size, so the big funnel shrinks to one scoring pass plus the simple diversity rules Instagram and TikTok describe, such as no long runs from one author or creator ([Instagram: Ranking explained](https://about.instagram.com/blog/announcements/instagram-ranking-explained); [TikTok Newsroom](https://newsroom.tiktok.com/en-us/how-tiktok-recommends-videos-for-you)). A ranked list cannot be paged with a keyset cursor, because scores change between requests. Ranking the whole window at once avoids that problem.

Precedent strongly favours keeping the chronological view close at hand. Twitter added a one-tap switch back to latest-first in 2018 ([9to5Mac](https://9to5mac.com/2018/12/18/twitter-chronological-timeline-button-ios/)). Facebook launched a chronological Feeds tab in 2022, with Zuckerberg calling not missing friends' posts one of the most requested features ([ITV News](https://www.itv.com/news/2022-07-21/facebook-unveils-new-look-home-in-app-refresh-without-suggested-posts)). Instagram's Following view shows 30 days of posts in chronological order ([Instagram: Ranking explained](https://about.instagram.com/blog/announcements/instagram-ranking-explained)). The trade-off is real. In a large *Science* experiment, moving Facebook and Instagram users to chronological feeds substantially reduced their time spent ([Guess et al., Science 2023](https://doi.org/10.1126/science.abp9364)), although a later critique questions how stable the comparison feed was during the study ([arXiv 2409.18393](https://www.arxiv.org/pdf/2409.18393)). Very large platforms in the EU must offer a feed option that does not rely on profiling ([DSA Article 38](https://www.springlex.eu/en/packages/dsa/dsa-regulation/article-38/)). That rule does not reach an app this size, but it reflects the norm.

Apple News is the best model for a small app. **Its recommendations come from information stored on the device, and reading history stays there** ([Apple News & Privacy](https://www.apple.com/legal/privacy/data/en/apple-news/)). Since the phone already loads the window, "For you" can score each item locally by the topics, countries and sources the reader opens, plus recency and the server's existing `importance`, then apply a no-two-in-a-row rule. That needs no account, no reading history on the server, and no extra AI call, so the project's one-AI-call-per-article principle stays intact. This is a design inference; no source found compares on-device and server ranking quality for small catalogs. The sequence helps here too: "unseen" means a sequence above the reader's mark, so For You can lift unseen items without any new server state. `docs/decisions.md` already places For You after the MVP, so nothing about it needs deciding now.

## The change is one column, one index and one parameter

The server side is small. Add a nullable integer `feed_seq` with a unique index. In the summarizer's existing UPDATE, set it to one more than the current maximum when `is_news` becomes 1 and the column is still empty; never change it afterwards, so a regenerated summary does not jump to the top. Backfill the rows that are already visible once, in `summarized_at, id` order. The feed then orders by `feed_seq DESC`. The opaque cursor carries a single integer, and the new-items check becomes `after=<feed_seq>` in place of `since=<ISO time>`, returning the items (or just their count) above that number. Keep the 7-day window on publication date as the stale-item guard. One rare side effect is that a very late item disappears from near the top when it reaches seven days old. On the phone, the work is the pill. The app saves the highest number it holds, polls on resume and about once a minute while open, shows "N new" when the reader is scrolled down, inserts directly at the top, and reloads from the top when the check reports more than one page.

Following the project's own rule (report what you observed, not what compiled), three checks would settle it. First, run two summarizer batches at the same time against the local D1 and confirm their sequence numbers are distinct and increase in commit order. That tests the single-writer inference above. Second, confirm D1 accepts the subquery inside the UPDATE, and `RETURNING` if it is used; neither was verified in this research. Third, repeat the overnight measurement. Under the new order, the number of overnight items that land below the previous top item should be zero, against 12 of 25 today. Process matters too. This reverses two agreed decisions, "show the latest published items by date" (2026-10-11) and the API ordering by `published_at` (2026-10-14). So the pull request needs to update `docs/decisions.md` and `docs/contract.md`, and because the API is item 1, Roman reviews it.

## Conclusion

The app does not have a pagination bug. It has a key-choice bug. Every symptom (late items buried mid-list, a "new" check that undercounts, a cursor that cannot reach them) comes from using a time the source supplies for a list that grows in the order the app discovers items. Mastodon learned this in 2018 and Bluesky restated it in 2026, and the fix in both is to let the server's own order govern position while the source's date stays on the label. The choice is less "A, B or C" than "one key or several". A single number that only rises can do the work of sort order, scroll cursor, "N new" count and last-seen mark, and every component built on it inherits the same guarantee.

The sequence is also the cheapest way to keep later options open. Delta sync for offline reading, "updated" badges, an unread count and an on-device "For you" all need a reliable answer to "what is new since I last looked", and the sequence provides it. Choosing publication order now would save one column and keep tidy dates on the cards. The cost is that readers can silently miss about half of overnight news, and the number of late items grows with every source the fetcher adds.
