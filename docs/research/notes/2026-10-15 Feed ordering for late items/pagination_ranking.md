# Pagination consistency with late inserts, and layering a ranked "For you" feed on a chronological one

Context: a small news app (~500 items in a 7-day window, ~50 to 70 new per day). The feed is the main screen. Today's contract (`docs/contract.md`, read 2026-10-15) sorts `GET /articles` by `published_at` descending with `id` as the tie-breaker, uses an opaque `cursor`, and has a `since=<ISO time>` check that filters on publication time. Options under consideration: (A) the server sorts by arrival time, (B) publication order plus a "new since last visit" block, (C) a server-assigned monotonic sequence with ordering on the client.

Source-access notes: blog.x.com returned HTTP 403 and developer.x.com returned HTTP 402 to direct fetches, so the Twitter 2023 blog numbers and the Twitter v1 timelines guide are cited through search-result extracts. They are marked "(via search extract)". The Bluesky timestamps guide redirected to an empty page on direct fetch, so it is also cited via search extract.

## 1. Offset vs keyset/cursor pagination: what breaks when rows arrive, especially rows inserted into the middle of the sort order

### Takeaway
Offset pagination produces duplicates or skips whenever rows are inserted or deleted ahead of the reader's position. Keyset/cursor pagination keeps each page stable and never duplicates or skips existing rows. However, a forward-only cursor can never return a row whose sort key lands behind the cursor, in the region already read. A "since <time>" check on the same key misses that row too. None of the big API providers' docs (Stripe, Shopify, GitHub, Google AIP-158) give an explicit consistency guarantee for concurrent inserts. The robust documented patterns are an ID that grows in arrival order (Twitter `since_id`, Mastodon `since_id`/`min_id`, Slack's "unique, sequential column"), or a sort key clamped to the server's arrival time (Bluesky `sortAt`).

### Cited Findings
**Offset failure modes**
- Slack (Michael Hahn, published 2017-08-15, updated 2020-06-25; pre-2020 core, still accurate): offset pagination is "unstable with concurrent writes": "the page window becomes unreliable, potentially skipping or returning duplicate results." Example: when paging a channel's newest messages, if 10 messages arrive after page one, page two repeats page one's results. — [Slack Engineering](https://slack.engineering/evolving-api-pagination-at-slack/)
- Slack: offset also scales poorly. "the database still has to read up to offset + count rows from disk, before discarding the offset and only returning count rows." Offset's real advantages are total counts and jumping to page N. — [Slack Engineering](https://slack.engineering/evolving-api-pagination-at-slack/)
- Use The Index, Luke (Markus Winand, 2014-08-06, updated 2023-09-08): "The idea to use the number of rows seen to skip over them later is simply wrong"; if rows are inserted between page fetches "you'll get duplicates." The flaw is the interface (page number or skip count), so no database can fix it. — [Use The Index, Luke: No Offset](https://use-the-index-luke.com/no-offset)
- Use The Index, Luke: with offset, "the pages drift when inserting new sales because the numbering is always done from scratch." — [Use The Index, Luke: Fetch next page](https://use-the-index-luke.com/sql/partial-results/fetch-next-page)
- Twitter v1 "Working with timelines" guide (v1-era, pre-2020): fixed-size page paging fails because new items keep arriving at the front. If 5 or more Tweets were added between calls, later calls would eventually return everything from the first request, making it redundant. — [Twitter developer docs, v1 timelines guide (via search extract)](https://developer.twitter.com/en/docs/twitter-api/v1/tweets/timelines/guides)

**Keyset/cursor mechanics and requirements**
- Use The Index, Luke: the seek method "uses the values of the previous page as a delimiter"; with it you "will also get stable results if new rows are inserted." — [Use The Index, Luke: Fetch next page](https://use-the-index-luke.com/sql/partial-results/fetch-next-page)
- "Paging requires a deterministic sort order". A non-unique key such as a date needs a unique tie-breaker ("just add any unique column(s) and extend the index accordingly"), e.g. `WHERE (sale_date, sale_id) < (?, ?) ORDER BY sale_date DESC, sale_id DESC` with index `(sale_date, sale_id)`. Row-value support varies by database: PostgreSQL and Db2 use it with indexes, MySQL cannot use it as an index access predicate, and the article gives an equivalent plain-comparison form for those. — [Use The Index, Luke: Fetch next page](https://use-the-index-luke.com/sql/partial-results/fetch-next-page)
- Keyset limitations: you "cannot fetch arbitrary pages", and browsing backwards needs reversed comparisons. Both are acceptable for infinite scroll. — [Use The Index, Luke: Fetch next page](https://use-the-index-luke.com/sql/partial-results/fetch-next-page)
- Slack: "The cursor must be based on a unique, sequential column (or columns) in the source table"; there is no total count and no jumping to a page. Slack's cursor is opaque Base64 (e.g. `user:W07QCRPA4`), so each endpoint can change its scheme, even to an encoded offset, without breaking clients. A cursor can encode several positions, e.g. one per shard. — [Slack Engineering](https://slack.engineering/evolving-api-pagination-at-slack/)
- Stripe: `starting_after` and `ending_before` take an object ID and return objects "in reverse chronological order"; `has_more` signals the end. The page makes no statement about objects created during pagination. — [Stripe API: Pagination](https://docs.stripe.com/api/pagination)
- Shopify GraphQL: cursors per node, `first/after`, `last/before` (only on "some" connections), `pageInfo.hasNextPage/endCursor`, max 250 per request, 25,000-object cap. It advises "specifying a sort key that matches the field used in the search." It makes no consistency statement. — [Shopify: Paginating with GraphQL](https://shopify.dev/docs/api/usage/pagination-graphql)
- GitHub REST: endpoints use `page`, `before/after` or `since`; clients should follow `link` header URLs as-is; oversize `per_page` is silently reduced. It makes no consistency statement. — [GitHub Docs: Using pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)
- Google AIP-158 (created 2019-02-18, changelog to 2025-07-08): page tokens must be opaque. "Base-64 encoding an otherwise-transparent page token is not a sufficient obfuscation mechanism". An empty `next_page_token` is "the only way to communicate 'end-of-collection'"; other parameters must match the original call; tokens may expire (three days is the rule of thumb); `total_size` may be an estimate. It says nothing about data changing between requests. — [AIP-158](https://google.aip.dev/158)

**Patterns for "new since" and late arrivals**
- Twitter v1 guide: set `since_id` to the greatest ID already processed ("not inclusive"); page older items with `max_id` = lowest seen ID minus 1. Using both lets apps avoid redundant data "while retaining the ability to iterate over the entire available contents." Tweet IDs are time-ordered (Snowflake). — [Twitter developer docs, v1 timelines guide (via search extract)](https://developer.twitter.com/en/docs/twitter-api/v1/tweets/timelines/guides)
- Mastodon: `max_id` sets an upper bound, `since_id` "All results returned will be greater than this ID" (returns the newest results after the ID), and `min_id` "Returns results immediately greater than this ID", paginating forward from it. That is the gap-free way to walk a backlog oldest-first. IDs are "usually using a variant of Snowflake ID", sortable by length then lexically. Next/prev links come in an RFC 8288 `Link` header. — [Mastodon API guidelines](https://docs.joinmastodon.org/api/guidelines/)
- Bluesky defines three timestamps. `createdAt` is author-supplied and can be any value, so backdating is possible, and a far-future value "will always sort to the top". `indexedAt` is set by the server ("first seen"). Bluesky recommends `sortAt` = the earlier of the two, i.e. use createdAt unless it is in the future. A stricter option is making sortAt nullable and leaving "null" posts out of chronological lists. Backdated posts still sort at their old time. — [Bluesky docs: Timestamps (via search extract)](https://docs.bsky.app/docs/advanced-guides/timestamps)
- Bluesky `getTimeline` cursor = UTC timestamp + CID (CID is the tie-breaker); "its format is considered to be an implementation detail of the service" (devinivy, 2023-11-15). Cursors only page into the past. A "search direction" / fetch-newer feature has been requested since 2023-11-07, called "by far the most common feature request" by a client dev, and was still unimplemented as of a 2026-02-27 comment (452 upvotes). Maintainer bnewbold noted clients could get "janky and out-of-order" when switching scroll order. — [atproto discussion #1834](https://github.com/bluesky-social/atproto/discussions/1834)

**Monotonic sequences on the project's stack (SQLite / D1)**
- SQLite without AUTOINCREMENT gives rowid = max+1. This is monotonic only "as long as you never use the maximum ROWID value and you never delete the entry in the table with the largest ROWID"; otherwise deleted values "might be reused". With `AUTOINCREMENT`, rowids are "guaranteed to be monotonically increasing" and never reused (gaps are possible). Only committed values count; rolled-back ones can be reused. The current max is tracked in `sqlite_sequence`, which tracks INSERTs only, not UPDATEs. — [SQLite: Autoincrement](https://www.sqlite.org/autoinc.html)
- Cloudflare D1: each database "is inherently single-threaded, and processes queries one at a time", backed by a single Durable Object. Excess requests queue and then return "overloaded". — [Cloudflare D1 limits (via search extract)](https://developers.cloudflare.com/d1/platform/limits)

### Inferences
- How each scheme behaves with a late item (derived from the definitions above, not stated by one source). Take an item whose sort key (`published_at`) is older than items the reader already has.
  - Offset: if it lands above the reader's offset, every later row shifts down one place, so the next page repeats one item. A delete above the offset skips one item.
  - Keyset on `published_at`: no duplicates or skips. If the item sorts after the cursor, it shows up on a later page. If it sorts before the cursor (the region already read), this pass never returns it.
  - `since=<last published_at>`: misses it, because its published_at is older than the watermark.
  - Pull-to-refresh of page 1: shows it only if it is among the newest ~20 by published_at.
  The current contract has exactly this gap.
- The general issue is "sort key ≠ visibility order". In this app, an article becomes visible to the feed only when the AI sets `is_news = 1`, which can be minutes to hours after `fetched_at`, and `fetched_at` can be days after `published_at`. This mirrors the classic database problem where an ID is assigned at insert but the row becomes visible at commit. Any "new since" watermark must be on the visibility event, not on publication or fetch time.
- Option C fits the documented patterns: a server-assigned integer stamped at the moment the item becomes visible, like Twitter/Mastodon `since_id` and Slack's "unique, sequential column". On D1, writes are serialized because the database is single-threaded. A sequence stamped in the same statement that sets `is_news = 1` would therefore be in commit order, with no out-of-order-commit hazard. Plain `rowid`/AUTOINCREMENT would NOT work here, because it is assigned at INSERT (fetch time), not at the visibility UPDATE, and `sqlite_sequence` ignores UPDATEs. A separate `visible_seq` column with a unique index is needed. This is an inference to verify in D1.
- Option A (sort by arrival) is Bluesky's `sortAt` idea taken further. It makes keyset and `since` exact, but the list order then disagrees with the dates shown on the cards. Bluesky's compromise (min(createdAt, indexedAt)) only protects against future-dated items, not late ones, so it does not solve this app's case.
- B and C combine cleanly: the client asks `since_seq=<max seq seen>`, the server returns every newly visible item regardless of published_at, and the client shows those items in a "New since last visit" block in publication order. The main list stays in publication order with a (published_at, id) keyset cursor. A late item then appears in the "new" block on the next check, and the main list picks it up on the next full reload.
- At this scale, ~500 items / 7 days at ~1 to 2 KB each without full text is roughly 0.5 to 1 MB (an estimate). A client could hold the whole window and order it locally, which removes the pagination-consistency problem for the main list.

### Gaps
- No primary source from Stripe, Shopify, GitHub or Google states what their cursors guarantee when rows are inserted behind the cursor. All four pages are silent on it, so the "late row is invisible to a forward cursor" behaviour is derived from first principles, not quoted.
- The Twitter v1 guide and the Bluesky timestamps page could not be fetched directly, so their wording comes from search extracts.
- I did not find a primary source on how Mastodon assigns IDs to remote statuses that arrive late (federation), which would be the closest real-world analogue to this app's late items.
- I did not verify in a running D1 instance that a `(SELECT MAX(visible_seq)+1 ...)` inside an UPDATE is atomic under D1's serialization. This is inferred from the single-threaded statement in the limits page.

## 2. Caching interplay: CDN/edge caching of feed pages and "since" checks

### Takeaway
The documented tools are short shared-cache freshness (`s-maxage`), `stale-while-revalidate` for content where brief staleness is OK, `no-cache` + ETag/304 for content that must be current, and conditional requests (`If-None-Match`/`If-Modified-Since`) for cheap "anything new?" polling. GitHub documents that 304s don't count against its rate limit and that stable sort orders make 304s more likely. No source found gives feed-specific CDN guidance for cursor pages.

### Cited Findings
- `s-maxage` "indicates how long the response remains fresh in a shared cache"; it is ignored by private caches and overrides `max-age` for shared caches. `private` means the response may be stored "only in a private cache". — [MDN: Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)
- `stale-while-revalidate` "indicates that the cache could reuse a stale response while it revalidates it". Example: `max-age=604800, stale-while-revalidate=86400`. — [MDN: Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)
- For "content that's generated dynamically, or that's static but updated often", MDN recommends `Cache-Control: no-cache`, which forces revalidation and lets the server answer `304 Not Modified`. It warns that omitting the header allows heuristic caching. — [MDN: Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)
- GitHub: "Most endpoints return an `etag` header, and many endpoints return a `last-modified` header". "Making a conditional request does not count against your primary rate limit if a `304` response is returned" (when authorized). A 304 is more likely with stable, specific requests, including a stable sort order. GitHub recommends webhooks over polling; if polling, "Poll only as often as you need to, on a fixed schedule." — [GitHub Docs: REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- Twitter v1 guide frames "what's new" as a `since_id` request against the greatest processed ID, not a time-based check. — [Twitter developer docs, v1 timelines guide (via search extract)](https://developer.twitter.com/en/docs/twitter-api/v1/tweets/timelines/guides)
- AIP-158: page tokens may expire, three days as a rule of thumb, and other request parameters must match across pages. That implies the cursor URL plus its parameters form a stable cache key. — [AIP-158](https://google.aip.dev/158)

### Inferences
- Page 1 (no cursor) is the only response whose content changes with each new item. Deeper keyset pages for (published_at, id) change only when a late item lands inside their range, which is rare. A long `s-maxage` on cursor pages and a short one (or `no-cache` + ETag) on page 1 is consistent with the MDN guidance.
- A "since" check keyed on a monotonic sequence (Option C) can be answered from a single integer, the current max `visible_seq`. That makes an ETag cheap: ETag = max seq, so an unchanged feed returns 304. This is a design inference, not a sourced pattern.
- If the CDN caches page 1 for N seconds, a client "new posts" check routed through the same cache will lag by up to N seconds. A fresh check should bypass the shared cache (`private`/`no-cache` on the check endpoint) rather than shortening the cache on the heavy feed page. This matches the user's own standing rule ("If the fresh value matters, read it client-side rather than shortening the cache").

### Gaps
- No primary source found with feed-specific CDN guidance for cursor-paginated APIs, i.e. how Twitter, Mastodon or Bluesky set Cache-Control on timeline pages.
- I did not check Cloudflare's cache-key docs for whether query strings such as `cursor=` are part of the default cache key.

## 3. Ranked feeds: architecture (candidate generation, ranking, mixing), and whether products keep a chronological tab

### Takeaway
Every large product documents the same pipeline. Candidate sourcing pulls in-network plus out-of-network items, a cheap first pass narrows to hundreds, a heavy model scores them, and heuristic rules then enforce diversity, filter content and mix in ads and modules. Twitter's open-sourced Home Mixer makes the separation explicit. "Following" and "Lists" share the same serving framework but skip the scoring stage and return reverse-chronological results, while "For You" adds sourcing, ~6,000 features, ML scoring and heuristics. Twitter (2018 toggle, 2023 tabs), Facebook (Feeds tab, 2022) and Instagram (Following, 30-day chronological) all kept or restored a chronological view after going ranked-by-default. The stated reasons are user demand ("most requested"), not missing friends' posts, and, in the EU, DSA Article 38's non-profiling option for very large platforms.

### Cited Findings
**Twitter/X (open-sourced 2023-03-31)**
- Home Mixer "builds and serves" the Home timelines on Product Mixer and powers three tabs. For You is a ranked mix of followed and recommended content. Following is "reverse chronological Tweets from people you follow". Lists is reverse chronological Tweets from List members. — [the-algorithm: home-mixer README](https://github.com/twitter/the-algorithm/blob/main/home-mixer/README.md)
- For You stages: candidate generation (Earlybird search index, User Tweet Entity Graph, CrMixer, Follow Recommendations); feature hydration ("Fetch the ~6000 features needed for ranking"); ML scoring; filters and heuristics (author diversity, in/out-of-network balance, feedback fatigue, dedup, visibility filtering); mixing (ads, who-to-follow, prompts). The Following pipeline lists Earlybird candidates, conversation ancestors, ads and WTF modules, with no scoring stage. — [the-algorithm: home-mixer README](https://github.com/twitter/the-algorithm/blob/main/home-mixer/README.md)
- Repo README: "Product surfaces at X are built on a shared set of data, models, and software frameworks"; search-index finds In-Network posts ("~50% of posts come from this candidate source"); a light ranker runs inside the search index and a heavy ranker (neural network) ranks after sourcing; visibility-filters handle "legal compliance, improve product quality". — [the-algorithm README](https://github.com/twitter/the-algorithm)
- 2023 blog: the system extracts "the best 1500 Tweets from a pool of hundreds of millions"; For You averages 50% In-Network / 50% Out-of-Network; in-network relevance uses a logistic regression model (Real Graph); graph-traversal heuristics serve ~15% of Home Timeline Tweets, with embedding approaches (SimClusters, TwHIN) the larger out-of-network source; the heavy ranker is a ~48M-parameter neural network optimizing positive engagement. — [Twitter Engineering blog, 2023 (via search extract; direct fetch 403)](https://blog.x.com/engineering/en_us/topics/open-source/2023/twitter-recommendation-algorithm)
- History: in Dec 2018 Twitter added the "sparkle" button to switch between the ranked default ("Top Tweets") and latest-first. The earlier settings toggle was buried and "automatically reverted to the algorithm timeline over time". Twitter said people who switched "enjoyed Twitter more". The sparkle icon was criticized as poor UX. — [9to5Mac, 2018-12-18](https://9to5mac.com/2018/12/18/twitter-chronological-timeline-button-ios/); [Social Media Today](https://www.socialmediatoday.com/news/twitter-rolls-out-new-button-to-easily-switch-between-chronological-and-alg/544674); [UX Collective critique](https://uxdesign.cc/the-worst-icon-to-ever-signify-a-feature-7b0fb74b748c) (pre-2020)

**Facebook / Meta**
- Engineering at Meta (2021-01-26), News Feed ranking. Inventory: posts since last login from friends, Groups and Pages, plus "unread bumping" (ranked but unseen older posts) and "action bumping" (older posts with new conversation); >1,000 candidates per user per day. Signals: "thousands". Predictions: multitask neural nets per engagement type. Score: weighted linear sum, with weights informed by surveys. Passes: Pass 0 (lightweight, narrows to ~500), Pass 1 (main personalized scoring), Pass 2 (contextual diversity rules). — [Engineering at Meta](https://engineering.fb.com/2021/01/26/core-infra/news-feed-ranking/)
- 2022-07-21: Meta launched a Feeds tab (friends, groups, Pages, favorites, chronological, no "Suggested for you", ads included) alongside a ranked "Home" positioned as a discovery engine. Zuckerberg called not missing friends' updates one of the "most requested" features. — [ITV News, 2022-07-21](https://www.itv.com/news/2022-07-21/facebook-unveils-new-look-home-in-app-refresh-without-suggested-posts); [GSMArena](https://www.gsmarena.com/facebook_adds_a_new_tab_called_feeds_which_is_sorted_chronologically-news-55151.php)

**Instagram**
- Adam Mosseri, 2023-05-31: "Instagram doesn't have a singular algorithm". Feed, Stories, Explore and Reels each have their own ranking. Feed steps: candidate set (recent posts from followed accounts, plus recommendations), "thousands" of signals, predictions of actions (time spent, comment, like, share, profile tap), scoring, and a rule against many posts from one person in a row. "Following" "will show you the last 30 days of posts from those you follow in chronological order"; Favorites rank higher. — [Instagram: Ranking explained](https://about.instagram.com/blog/announcements/instagram-ranking-explained)

**LinkedIn**
- 2019 engineering post: two-pass architecture. First-pass rankers (FPR) each select candidates from their inventory (network updates, jobs, sponsored), and a single second-pass ranker (SPR) merges and scores them into one list. FollowFeed (network updates) supplies >80% of feed updates and >95% of conversations. Objectives: likelihood to view, to participate, and timely feedback to creators. — [LinkedIn Engineering, 2019-06 (via search extract; pre-2020)](https://engineering.linkedin.com/blog/2019/06/community-focused-feed-optimization)
- A 2026 rebuild reportedly moved to LLM-based unified retrieval plus a transformer sequential ranker. This comes only from secondary summaries and is unverified. — [ZenML LLMOps summary](https://www.zenml.io/llmops-database/next-generation-feed-ranking-with-llms-and-sequential-transformers)

**TikTok**
- Newsroom, 2020-06-18. For You signals: user interactions (likes, shares, follows, comments, content created), video info (captions, sounds, hashtags) and device/account settings ("lower weight"). Finishing a longer video is a strong signal. "neither follower count nor whether the account has had previous high-performing videos are direct factors". Cold start: pick interest categories, or get "a generalized feed of popular videos". Diversity: generally no two in a row with the same sound or creator, and deliberate out-of-interest items. The post does not mention a Following/chronological feed. — [TikTok Newsroom](https://newsroom.tiktok.com/en-us/how-tiktok-recommends-videos-for-you)

**Why products keep a chronological option**
- Guess et al., *Science* 2023: randomly moving consenting Facebook/Instagram users to reverse-chronological feeds during the 2020 US election "substantially decreased" their time spent and activity. It increased political and untrustworthy content, decreased uncivil content on Facebook, and did not significantly change polarization or knowledge over 3 months. — [CSMaP NYU summary](https://csmapnyu.org/research/academic-research/how-do-social-media-feed-algorithms-affect-attitudes-and-behavior-in-an-election-campaign); [DOI 10.1126/science.abp9364](https://doi.org/10.1126/science.abp9364)
- A later critique (Bagchi, Menczer et al.) argues the control condition shifted because Meta made 63 unreported "break-glass" changes to the ranked feed during the study. The critique concerns the misinformation conclusions more than time spent. — [arXiv 2409.18393](https://www.arxiv.org/pdf/2409.18393)
- EU Digital Services Act, Article 38 (OJ L 277, 27/10/2022): very large online platforms and search engines must offer, for each recommender system, at least one option "not based on profiling" (GDPR Art. 4(4)). Recital 94 says this option should be reachable directly where recommendations appear. — [DSA Article 38 (Springlex)](https://www.springlex.eu/en/packages/dsa/dsa-regulation/article-38/)
- In March 2026, EDRi filed a DSA complaint against Google/YouTube alleging the non-profiling option is "counter-intuitive and hard to access". This is an allegation, not a finding. — [EDRi complaint (PDF)](https://edri.org/wp-content/uploads/2026/03/EDRi-DSA-complaint-Youtube.pdf)

### Inferences
- The documented separation is "same candidate store and serving framework, two pipelines". The chronological tab is the candidate set with filters and no scoring, and the ranked tab adds a scoring and mixing stage on top. For this app, "For you" can be a second ordering of the same 7-day `is_news = 1` set. No new candidate source is needed until out-of-window or cross-topic recommendations are wanted.
- At ~500 candidates the big-platform funnel (hundreds of millions → 1,500 → ranked) collapses. The whole candidate set is smaller than Facebook's Pass-0 output (~500). A single scoring pass plus TikTok/Instagram-style diversity rules (no two in a row from the same source or country) is the relevant subset.
- Ranked feeds cannot use a keyset cursor on the score, because scores change between requests. Big products compute a ranked list per request and page through that snapshot. Bluesky's custom feeds let each feed define its own opaque cursor. For a small app, ranking the whole window client-side or returning it in one response avoids the problem.
- Precedent strongly favors keeping the chronological view, either as the default or one tap away. Every product surveyed that went ranked-by-default later added or restored a chronological option. The DSA rule does not apply at this app's size, but it signals the norm.

### Gaps
- I could not fetch the 2023 Twitter blog directly (403), so its numbers come from search extracts that agree with each other. The repo README confirms only the "~50%" in-network figure and the ~6,000 features.
- No primary source found stating why Twitter in 2023 split "For You"/"Following" into tabs, or what share of users choose chronological.
- I did not find Instagram's original 2016 rationale or its often-quoted "people miss 70% of their feed" figure in a primary source. The 2023 explainer does not contain it.

## 4. Lightweight personalization for small apps: on-device re-ranking vs server-side ranking with accounts; privacy

### Takeaway
The best-documented privacy-preserving model in news is Apple News. Recommendations are made from information stored on the device, activity is tied to a News-specific identifier rather than the Apple ID, and reading history stays on the device. Server-side ranking needs a persistent identity and moves reading history off the device, which brings consent, deletion and (in the EU at scale) DSA profiling obligations. The large-platform signal lists (dwell/finish, explicit follows, topic and author affinity, diversity rules) transfer to a small on-device re-ranker. I found no primary source that benchmarks on-device vs server ranking quality for small catalogs.

### Cited Findings
- Apple News: recommendations "are made based on the information stored on your device"; activity is associated with a News-specific identifier, "not associated with your Apple Account or linked to other Apple services". Exceptions: channel notifications and Apple News+ followed channels can be linked to the account. Users can clear history (Following > History > Clear) or reset the identifier. — [Apple News & Privacy](https://www.apple.com/legal/privacy/data/en/apple-news/)
- Apple News personalized newsletters: "on-device artificial intelligence" groups the user with thousands of others with similar interests; only aggregated interest data goes to Apple, so "Apple does not know your reading history". — [Apple News Newsletters & Privacy](https://www.apple.com/legal/privacy/data/en/apple-news-newsletters/)
- Signals the big systems weight, as candidates for a small re-ranker: TikTok weights finishing a video strongly and device/locale settings weakly, and does not use follower count directly. — [TikTok Newsroom](https://newsroom.tiktok.com/en-us/how-tiktok-recommends-videos-for-you). Instagram predicts time spent, likes, comments, shares and profile taps, and avoids runs from one author. — [Instagram: Ranking explained](https://about.instagram.com/blog/announcements/instagram-ranking-explained). Facebook combines predictions as a weighted sum, with weights partly from user surveys, and applies diversity in a final pass. — [Engineering at Meta](https://engineering.fb.com/2021/01/26/core-infra/news-feed-ranking/)
- TikTok cold start: explicit interest selection, else "a generalized feed of popular videos". — [TikTok Newsroom](https://newsroom.tiktok.com/en-us/how-tiktok-recommends-videos-for-you)
- DSA Art. 38 defines "profiling" by reference to GDPR Art. 4(4); the non-profiling obligation applies only to very large platforms. — [DSA Article 38 (Springlex)](https://www.springlex.eu/en/packages/dsa/dsa-regulation/article-38/)

### Inferences
- For a ~500-item window that the client already downloads, an on-device "For you" works like this. Score each item by affinity to the topics, countries and sources the user opened or read to the end, plus recency decay and the server's `importance`, then apply a "no two in a row from the same source/country" rule. No account, no server-side history and no extra AI calls are needed. That keeps the project principle "One AI call per article, run once on the server" intact. This is a design inference modelled on the Apple News privacy approach.
- Cold start can mirror TikTok: optional topic or country picks, otherwise fall back to the chronological feed or the existing `top` list.
- Server-side ranking becomes worth it only when cross-device sync or collaborative signals ("readers like you") are needed. Those need an identifier and move reading history to the server, which brings consent and deletion duties under GDPR. That is general knowledge; I did not source GDPR specifics in this research.

### Gaps
- No primary source found measuring on-device vs server-side ranking quality or engagement for small catalogs.
- No primary source found on minimum data needed for useful news personalization, e.g. how many reads before affinity beats recency.
- I did not research platform rules (App Store / Play) on storing reading history on-device. They are believed to be permissive, but this is unverified.

## 5. The "N new posts" pill / "Show new posts" pattern: not moving the list while the user reads

### Takeaway
The documented pattern is to never move content under the reader. When new items arrive and the user is not at the top, keep the viewport anchored, show a "New posts" pill (often with a count), and load or jump only when the user taps it. If the user is already at the top, new items can just appear. Instagram documented this in 2018. Twitter abandoned web auto-refresh after complaints. WCAG 2.2.2 requires a way to pause, stop or hide auto-updating content shown alongside other content. I found no Material Design or Apple HIG text that specifically prescribes the pill.

### Cited Findings
- Instagram (2018-03-22): "We've heard it can feel unexpected when your feed refreshes and automatically bumps you to the top." It tested a New Posts button: "Tap the button and you'll be taken to new posts at the top of feed – don't tap, and you'll stay where you are." At the same time it changed ranking so "newer posts are more likely to appear first in feed". — [Instagram: New Posts button](https://about.instagram.com/blog/announcements/new-posts-button-to-improve-instagram-feed) (pre-2020)
- WCAG 2.2 SC 2.2.2 (Pause, Stop, Hide): "For any auto-updating information that (1) starts automatically and (2) is presented in parallel with other content, there is a mechanism for the user to pause, stop, or hide it or to control the frequency of the update". Examples include "automatically updated weather information, news, stock price updates". Rationale: "Content that moves or auto-updates can be a barrier to anyone who has trouble reading stationary text quickly", including people with attention deficit disorders or reading disabilities. — [W3C: Understanding SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)
- Twitter turned off automatic refresh of the web timeline after years of complaints that tweets vanished mid-read, matching the apps, where tapping Home loads newest tweets. This comes from a secondary German trade source, undated in extract. — [OnlineMarketing.de](https://onlinemarketing.de/social-media-marketing/twitter-schafft-auto-refresh-ab)
- Open-source client implementations: a Pleroma/Kenoma issue asks to keep the reading position stable when new posts are added above, by compensating scroll offset, but not when already at the very top. — [Kenoma issue #9](https://git.pleroma.social/lambadalambda/kenoma/issues/9). A Minds bug report expects the "see latest posts" button to always take the user to the very top with new posts loaded. — [Minds engine issue #2392](https://gitlab.com/minds/engine/-/issues/2392)
- Bluesky clients want to fetch newer posts in the background and show them above the reading position. The API's backward-only cursors make this hard (see section 1). — [atproto discussion #1834](https://github.com/bluesky-social/atproto/discussions/1834)
- NN/g on infinite scroll: long endless pages suit browsing rather than goal-oriented finding, and restoring position after navigating back ("pogo-sticking") is a known problem. — [NN/g: Infinite scrolling tips (via search extract)](https://www.nngroup.com/articles/infinite-scrolling-tips/)

### Inferences
- The pill needs a cheap "anything new?" signal. A monotonic visibility sequence (Option C) gives an exact count of newly visible items ("3 new"), including late items with old publication dates. A `since=<published_at>` check undercounts them.
- In Option B, tapping the pill can scroll to the top and expand a "New since last visit" block ordered by publication time. The main list below stays untouched, which satisfies "don't move the list while reading". Late items appear in the block with their real (older) dates, so the block's label should say "new to you" or "added since", not "latest".
- Auto-inserting at the top is acceptable only when the user is already at scroll offset 0 (Kenoma guidance). Otherwise insertion above the viewport needs scroll-offset compensation or must wait for the tap. WCAG 2.2.2 effectively requires the tap-to-load option for a news feed that would otherwise auto-update.

### Gaps
- No Material Design 3 or Apple HIG section was found that explicitly specifies a "new content" pill or anchoring behaviour. I did not fetch HIG "Refresh content controls" or Android SwipeRefreshLayout guidance in this pass.
- No primary Twitter/X or LinkedIn design documentation for their "New posts" pill was found. The Twitter evidence is press coverage only.
- No user research (NN/g or other) found that measures the effect of content insertion above the viewport on reading or comprehension.
